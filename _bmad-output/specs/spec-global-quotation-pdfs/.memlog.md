- (capability) CAP-1: El asesor puede abrir un cotizador global desde la cuarta bottom tab, sin lead ni vehículo, para calcular únicamente Tarjeta de crédito con la lógica matemática existente.
- (capability) CAP-2: El asesor puede generar un PDF profesional sólo después de elegir lead y modelo, conservando el monto digitado y el resultado calculado en el documento.
- (capability) CAP-3: El sistema conserva cada PDF generado como histórico inmutable y permite verlo o descargarlo desde el contexto del lead/cotizador.
- (capability) CAP-4: Antes de enviar, el sistema garantiza que el archivo corresponde exactamente a los valores actuales; si cambiaron, genera un PDF actualizado y pide confirmación humana.
- (capability) CAP-5: El envío futuro de una cotización confirmada usa exclusivamente el canal WhatsApp de clientes, con auditoría e idempotencia aisladas del First Contact y de los recordatorios.
- (decision) La navegación mantiene exactamente cuatro bottom tabs: Resumen, Nuevo lead, Mi QR y Cotización; WhatsApp sale de las tabs y queda en el menú de usuario existente.
- (decision) El cálculo de Tarjeta de crédito sigue dependiendo sólo de monto, modalidad y plazo; se reutiliza lib/financial/card-quote.ts sin cambiar factores, fórmulas, precisión ni golden tests.
- (decision) La simulación no se persiste; el histórico nace sólo cuando Generar PDF o Enviar cotización produce un PDF válido.
- (decision) Generar PDF exige lead y modelo por contexto documental, pero nunca infiere el monto desde el catálogo ni exige lead/vehículo para calcular.
- (decision) Cada PDF histórico es inmutable y no se sobreescribe; el path recomendado es quotations/{lead_id}/{quote_file_id}.pdf en un bucket privado dedicado, sujeto a verificación de buckets remotos durante implementación.
- (decision) La vista previa reutiliza el PdfViewer existente y una route autenticada de LeadFlow; la descarga usa la misma route con nombre seguro y Content-Disposition.
- (decision) El renderer recomendado es pdf-lib server-only para un PDF determinista, moderno y de una página cuando quepa; será la única dependencia nueva justificada del slice PDF y no se usará Excel/HTML-print.
- (decision) La selección explícita de modelo es obligatoria cuando el lead tiene varios modelos; con uno se preselecciona, sin elegir silenciosamente entre varios.
- (decision) El envío futuro usa sendWhatsappDocument y el cliente Evolution existente; nunca usa la instancia de recordatorios ni cambia Evolution.
- (constraint) No implementar NovaCredit ni tocar First Contact, colores, Push, recordatorios, scoring, purchase journey, infraestructura, datos remotos o producción en este incremento de especificación.
- (constraint) La autorización y ownership siguen el patrón requireAdvisor/requireAdvisorOrRedirect y las policies existentes; el navegador no escribe directamente Storage ni metadata.
- (constraint) La validación de frescura debe reconstruir y comparar el snapshot en servidor; el estado React sólo puede mejorar la UX, nunca ser la autoridad.
- (assumption) El modelo del lead se resolverá contra el catálogo existente por ID/nombre real y se persistirá también como nombre snapshot para que el documento histórico no cambie si el catálogo se renombra.
- (assumption) El PDF podrá usar únicamente assets de marca ya presentes y aprobados; si no existe un logo autorizado, se usará composición tipográfica sin inventar marca.
- (question) Durante el slice de implementación debe confirmarse mediante preflight qué bucket privado existente puede reutilizarse o si se crea quotations como bucket privado dedicado; no se inventará un bucket remoto ni se tocará producción durante esta ejecución.
- (question) El dueño debe aprobar el nombre comercial final visible del PDF y disclaimer si desea algo distinto de Cotización / Simulación referencial; el contenido mínimo ya queda cerrado.
