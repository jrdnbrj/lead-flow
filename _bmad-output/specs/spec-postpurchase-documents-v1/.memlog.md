- (event) Se eligió modo express/headless: el usuario entregó alcance, límites y preguntas concretas para una mini-spec.
- (note) Discovery contrastada con project-context, purchase_cases, purchase_case_milestones, PostPurchasePanel, migrations 068/070/073/074/075/077, quote_files y helpers de Storage.
- (note) El baseline actual separa purchase_cases 1:1 por lead de 13 milestones; PostPurchasePanel es la integración existente y no hay documentos postcompra.
- (note) quote_files usa bucket quotations privado, paths UUID por lead, metadata JSONB y route autenticada; su dominio es cotización y no debe reutilizarse como expediente postcompra.
- (note) El catálogo vehiculos es público y no es adecuado para documentos privados; no se encontró un patrón de carga de archivos existente.
- (capability) CAP-1: El asesor puede adjuntar manualmente un documento permitido a un purchase_case comprado para mantener su expediente operativo. Éxito: metadata y objeto privado quedan asociados al caso del asesor sin alterar leads ni milestones.
- (capability) CAP-2: El asesor puede consultar, abrir y descargar los documentos activos de su purchase_case. Éxito: otro owner no puede obtener metadata, objeto ni URL de un caso ajeno.
- (capability) CAP-3: El asesor puede reemplazar documentos de cardinalidad única y agregar documentos de tipos múltiples. Éxito: nunca hay más de un activo en tipos únicos y la trazabilidad previa se conserva.
- (capability) CAP-4: El asesor puede retirar lógicamente un documento del expediente. Éxito: deja de listarse y no genera acceso nuevo, conservando trazabilidad mínima.
- (capability) CAP-5: El expediente sigue siendo legible cuando PURCHASE_DECISION está REVERTED y bloquea mutaciones hasta reactivarse. Éxito: documentos y purchase_case permanecen intactos y la reactivación reutiliza el mismo caso.
- (decision) Los tipos v1 son INVOICE, FONDO_VIAL, RAMV, PAYMENT_ORDER, PAYMENT_RECEIPT, REGISTRATION y OTHER como catálogo controlado en base de datos.
- (decision) INVOICE, FONDO_VIAL, RAMV y REGISTRATION admiten un único documento ACTIVE con reemplazo; PAYMENT_ORDER, PAYMENT_RECEIPT y OTHER admiten múltiples documentos ACTIVE.
- (decision) El modelo usa estados ACTIVE, REPLACED y DELETED, deleted_at/deleted_by y replaced_by; no usa event sourcing ni versionado numérico separado.
- (decision) Reemplazar inserta un nuevo documento con UUID y marca el anterior REPLACED en una operación server-side atómica; el archivo anterior no se borra.
- (decision) Eliminar significa soft delete: marca DELETED, excluye el documento de listados y bloquea nuevas URLs; el objeto privado conserva su asociación para trazabilidad y evita inconsistencias DB/Storage.
- (decision) El nuevo bucket dedicado purchase-documents será privado, separado de quotations y vehiculos; path estable: purchase-cases/{purchase_case_id}/{document_id}/{safe_extension}.
- (decision) La primera versión permite application/pdf, image/jpeg, image/png e image/webp, con límite de 10 MiB; el servidor valida MIME, tamaño y firma básica antes de persistir.
- (decision) La carga usa upload UUID con upsert=false y luego inserción/replace server-side; si la mutación de metadata falla, se elimina compensatoriamente el objeto recién subido.
- (decision) La lectura/descarga pasa por una route autenticada que valida owner y estado; si usa signed URL, ésta es efímera de 5 minutos, no se persiste ni se publica.
- (decision) Todas las mutaciones validan sesión, ownership, purchase_case activo y PURCHASED en servidor/RPC; REVERTED permite lectura pero no carga, reemplazo ni eliminación.
- (decision) PostPurchasePanel incorpora una sección compacta Documentos, sin nueva navegación; la carga de un documento nunca completa ni modifica un milestone.
- (constraint) No tocar leads, PURCHASE_DECISION, purchase_cases/milestones existentes, First Contact, cotizaciones, Push, reminders, Evolution, OCR, IA ni automatizaciones externas.
- (assumption) La eliminación lógica satisface v1; una exigencia legal o comercial de destrucción física requeriría una decisión de retención separada.
- (question) ¿La política del negocio exige destrucción física del binario o basta con ocultarlo mediante soft delete manteniéndolo privado para trazabilidad?
- (question) Antes de implementar debe verificarse que el nombre purchase-documents no colisione con buckets remotos; si existe, debe elegirse otro nombre sin modificar buckets existentes.
- (event) La mini-spec se derivará con P0/P1 explícitos, criterios de aceptación, migración forward-only y slices pequeños; no se implementa código ni se toca Supabase.
- (event) Pass 1 coherence: cada capability tiene intent y success; constraints excluyen diseños alternativos; non-goals y success signal son concretos; el kernel queda lean.
- (event) Pass 2 preservation: se conservaron las 14 preguntas técnicas, tipos v1, cardinalidad, Storage privado, RLS, signed access, reversión, milestones manuales, UX y alcance futuro diferido.
- (event) Decisión cerrada: v1 usa soft delete trazable; no se destruyen físicamente binarios ni se implementa retención/purga en este slice.
- (event) Decisión cerrada: reemplazo de tipos únicos conserva histórico REPLACED; tipos múltiples no se reemplazan implícitamente.
- (event) Decisión cerrada: PURCHASED habilita mutaciones; REVERTED conserva lectura y bloquea mutaciones; reactivación reusa el mismo purchase_case.
- (event) Mini-spec lista para aprobación humana; no se implementó código, no se creó migration, no se aplicó nada, no se modificó Supabase, no se desplegó y no se llamó Evolution/WhatsApp.
