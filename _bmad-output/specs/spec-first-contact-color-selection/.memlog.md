---
topic: Selección opcional de color y foto por vehículo para First Contact
goal: Permitir elegir antes del envío la foto por color de hasta tres vehículos sin romper First Contact, E3 ni el comportamiento histórico
updated: 2026-09-02T20:29
---

- (direction) El incremento es una mini-spec brownfield para aprobación humana; no implementa código, migraciones, configuración, deploy ni mensajes reales.
- (note) El estado real actual usa Next.js App Router, Supabase, First Contact E3, catálogo de colores y assets por color; project-context y architecture spine son contratos adoptados.
- (capability) CAP-1: El asesor puede escoger opcionalmente Predeterminada o un color para cada una de las primeras tres posiciones de vehículos antes de iniciar First Contact, viendo la miniatura efectiva.
- (capability) CAP-2: El sistema puede resolver una foto específica modelo+color por posición y mantener la ficha técnica independiente del color.
- (capability) CAP-3: Al iniciar First Contact el sistema persiste el recurso resuelto por item E3 y los reintentos reutilizan ese snapshot sin cambiar de foto.
- (capability) CAP-4: El sistema conserva send-once, idempotencia, efectos externos, orden MESSAGE y recursos por modelo, fallos independientes e invariantes históricas.
- (constraint) La autoridad de modelos continúa siendo leads.car_models como text[] ordenado; el alcance de recursos continúa siendo slice(0, 3).
- (constraint) La creación/edición general del lead, la ficha técnica, Push, reminder WhatsApp, Evolution, inbound, catálogo administrativo y First Contact histórico quedan fuera del cambio.
- (constraint) Las selecciones y URLs no son controladas por el navegador: el servidor valida ownership, posición, modelo y pertenencia color→modelo antes de persistir o enviar.
- (decision) Usar lead_vehicle_color_selections con una fila máxima por lead_id + vehicle_index; ausencia de fila representa Predeterminada y resetear elimina la selección.
- (decision) Usar car_model_color_assets existente para PHOTO; no crear otra tabla de colores ni modificar el catálogo general.
- (decision) Persistir resource_snapshot JSONB server-only en lead_contact_operation_items, incluyendo identidad de modelo/color/asset, locator inmutable, origen, nombre y digest.
- (decision) La resolución será color específico activo, luego el resolver predeterminado actual, luego su fallback legacy y finalmente NOT_AVAILABLE; si falta la foto del color no bloquea.
- (decision) El selector se integra como una superficie compacta y reutilizable del FirstContactSummary y como preenvío del botón existente Enviar del dashboard, sin navegación ni rediseño general.
- (assumption) Una selección puede actualizarse libremente antes de crear la operación; una vez creada la operación, su snapshot es autoridad y la UI no permite alterar el envío histórico.
- (assumption) Para preservar bytes históricos, futuros cambios de assets deben usar nueva fila/storage_path inmutable y conservar el locator anterior; no se permite sobrescribir silenciosamente un objeto referenciado.
- (question) Confirmar sólo durante aprobación si Predeterminada debe significar explícitamente el comportamiento actual blanco-first o si el negocio exige otra foto genérica; la spec conserva el comportamiento actual por defecto.
- (note) La diferencia detectada es que el lenguaje de producto dice foto genérica, pero el código actual prioriza PHOTO activa del color blanco antes del asset de modelo y legacy; no debe alterarse.
- (event) Pass 1 de coherencia: kernel y companion propuestos con capacidades identificadas, restricciones que cambian diseño, non-goals y señal demostrable.
- (event) Pass 2 de preservación: se conservaron claims del input sobre UX, resolución, snapshot, E3, máximo tres, legacy, historial, seguridad, pruebas y fuera de alcance.
- (event) Mini-spec finalizada; artefactos validados, referencias adoptadas presentes y git diff --check PASS; queda pendiente aprobación humana antes de implementación.
