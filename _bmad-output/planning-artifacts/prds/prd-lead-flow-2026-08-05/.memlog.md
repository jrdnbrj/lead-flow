- (event) Jornada confirmada: cliente llega al concesionario, conversa con el primer asesor disponible, se captura el formulario actual cuando la conversación supera una consulta simple, el lead queda guardado sin acción automática y el asesor debe recordar enviar WhatsApp, responder o programar seguimiento.
- (event) La ficha técnica del vehículo todavía no se envía en el botón actual, pero el flujo futuro de primer contacto deberá contemplar su envío junto con información y fotos del vehículo.
- (hypothesis) La pérdida principal ocurre después de guardar el lead: el asesor olvida o posterga el primer contacto y las respuestas posteriores por falta de tiempo, por lo que la próxima acción ejecutada es el núcleo del PRD.
- (assumption) Cuando el asesor no configura una próxima acción, el lead podría permanecer sin acción en lugar de bloquear la captura; esto requiere decisión de negocio antes de cerrar los requisitos de seguimiento.
- (decision) Guardar un lead nunca se bloquea por no tener próxima acción; queda visible como Sin próxima acción y no genera Push hasta que el asesor programe una acción.
- (decision) Hecho se interpreta según la acción: llamada y cotización se marcan manualmente; WhatsApp enviado desde LeadFlow solo se considera hecho cuando Evolution acepta el envío; errores mantienen la acción pendiente.
- (decision) Una respuesta entrante no cancela el trabajo futuro sin reemplazo: debe generar una nueva próxima acción sugerida; el tipo y el plazo exactos de esa sugerencia quedan abiertos para el PRD.
- (decision) El primer contacto intentará enviar mensaje, fotos y ficha técnica; si falta algún recurso, se envía lo disponible y no se bloquea todo el contacto.
- (decision) El segundo bloque comienza cuando el asesor registra que el cliente decidió comprar, aunque el registro ocurra después de la decisión real; el PRD del piloto cubrirá el primer bloque y no modelará el proceso completo de pago, promociones, accesorios, documentos o matrícula.
- (assumption) El registro de decisión de compra será una acción posterior y manual del asesor, no una inferencia automática del chat; el momento registrado representará cuando el asesor tuvo tiempo para activarlo, no necesariamente cuando el cliente decidió.
- (decision) Se permite posponer una acción varias veces, con opciones rápidas iniciales de una hora y para mañana; el comportamiento conserva la acción y registra la reprogramación.
- (decision) Ignorar cierra únicamente la acción actual, elimina sus recordatorios y no marca el lead como perdido ni cerrado.
- (assumption) Para mensajes entrantes se propone crear o actualizar una única acción Responder al cliente por lead, con primer vencimiento en una hora; la acción puede cerrarse como No requiere respuesta sin nota obligatoria. Requiere confirmación del usuario antes de cerrar la sección.
- (decision) Se confirma el manejo de mensajes entrantes: cada lead tendrá como máximo una acción Responder al cliente; la primera alerta vence una hora después, puede posponerse una o varias veces y puede cerrarse como No requiere respuesta sin cambiar el estado comercial.
- (decision) Una respuesta enviada desde el WhatsApp nativo puede marcarse manualmente como Hecho en LeadFlow, sin nota obligatoria; se distingue de una respuesta verificada por Evolution.
- (decision) Se confirma que el primer contacto será explícito, único e idempotente por lead; intentará enviar mensaje, fotos y ficha técnica disponible, y permitirá envío parcial si falta algún recurso.
- (decision) Las acciones de llamada, WhatsApp, cotización u otra acción podrán programarse con fecha y hora exactas, respetando la zona horaria America/Guayaquil; el caso de responder mensajes mantiene su primer vencimiento una hora después del mensaje entrante.
- (decision) Si varias acciones vencen al mismo tiempo, se usará una notificación separada por acción, sin duplicar la misma acción; el WhatsApp al asesor queda como COULD para escalamiento controlado, no como canal principal ni requisito obligatorio.
- (decision) Se confirma que Cliente decidió comprar será una acción manual simple en la tarjeta del lead; registra el momento en que el asesor lo marca y no intenta inferir la decisión desde el chat.
- (decision) El PRD no fija si la sincronización corporativa usará automatización de navegador o reproducción de solicitudes HTTP internas; esa es una decisión de arquitectura posterior. El requisito de producto es una operación autorizada, segura, idempotente y verificable.
- (decision) Se fija como criterio operativo que el backend genere la solicitud Push dentro de un margen de un minuto respecto a la hora programada, sin afirmar entrega física al dispositivo.
- (decision) Si una suscripción Push es inválida o revocada, la acción pendiente se conserva, se registra el estado, se ofrece reactivación explícita y el WhatsApp de escalamiento permanece como capacidad COULD.
- (decision) Se confirma como objetivo operativo inicial que al menos 90% de los leads tenga una próxima acción definida; los demás indicadores se interpretarán contra la línea base de las primeras dos semanas y las ventas serán un resultado observado.
- (event) PRD finalized
